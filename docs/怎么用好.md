# 怎么用好这个检测器

这份文档不讲技术细节，只讲**实际使用时会踩的坑**和**怎么让结果更可信**。

---

## 一、先明确它是什么

它是一个**本地运行的文体分类器**，判断一段文字"像不像 AI 写的"。

它**不是**：
- 学术诚信的判决工具
- 能追平 Turnitin / GPTZero 的同类产品
- 能识别"任何 AI 写的文本"的万能检测器

它**是**：
- 一个不需要联网、不需要 GPU、装个 numpy 就能跑的信号源
- 在**它见过的文体**上相当准（如说明文、论述文 F1 约 0.98）
- 在**它没见过的文体**上会静默失灵（见第四节）

---

## 二、提高准确率的三个做法

### 1. 给足长度

| 长度 | 中文 F1 | 建议 |
|---|---|---|
| 200 字以上 | 0.9896 | ✅ 最可靠 |
| 80–200 字 | 0.9775 | ✔ 较可靠 |
| 40–80 字 | 0.9626 | ⚠ 中等 |
| 40 字以下 | — | ⚠ 概率被主动拉向 0.5 |

短文本不是"模型差一点"，而是**信息本来就不够**。程序会把概率往 0.5 收缩，
这是故意的——不想给你虚假的确定性。

### 2. 同内容多测几段

如果一段文字分成了几个自然段，**分开测**比合起来测更能看出问题。
有时候某一段的 AI 特征特别集中。

### 3. 看 `confidence` 字段，不只看 `ai_probability`

```json
{"ai_probability": 0.74, "bucket": "高", "confidence": "中(80-200字 F1~0.98)"}
```

`confidence` 告诉你**这个长度的判断有多可信**。0.74 配上"低(<40字)"，
实际可信度远不如 0.65 配上"高(长文本)"。

---

## 三、它会给你"拒绝"而不是分数

遇到以下输入，它**不会编造一个概率**，而是明确告诉你为什么：

```json
{"ai_probability": 0.0, "error": "not_natural_language"}
```

| `error` | 意思 | 怎么办 |
|---|---|---|
| `no_meaningful_content` | 空的、纯符号、纯空白 | 贴正文进去 |
| `not_natural_language` | JSON / HTML / 代码 / 纯数字 | 只贴自然语言 |
| `repetitive_content` | 大段内容重复 | 检查是不是复制了两遍 |

**为什么要这样**：早期版本会给 HTML 片段打 0.32、给重复 500 遍的句子打 0.97「高」。
那个数字看起来像结论，其实毫无意义。宁可说"我判断不了"。

## 四、什么时候它可能失灵（重要）

### 文体盲区

模型学的是**文体的措辞特征**，不是"AI 味"这个抽象概念。所以：

| 文体 | 识别情况 |
|---|---|
| 说明文 / 论述文 | ✅ 很好 |
| 公文 / 邮件 / 会议纪要 | ✅ 好（补过数据） |
| 实用指南（选购/装修/保养） | ✔ 还行，换新主题会漏 |
| 营销文案（详情页/软文） | ✔ 还行，换新主题会漏 |
| 社交文体（小红书/微博/知乎） | ✔ 还行，换新主题会漏 |
| **完全没见过的文体** | ❌ 可能完全失灵 |

**判据**：如果你贴的文本**内容非常具体、几乎没有套话**，
那它可能漏判——因为模型能抓的"AI 痕迹"本来就少。

### 非中英语言

语言判断是**按汉字占比**做的，分不出中日。

| 你贴的 | 实际走哪个模型 |
|---|---|
| 中文 | 中文模型 ✅ |
| 英文 | 英文模型 ✅ |
| **日文**（含汉字） | **中文模型** ❌ |
| 韩文 / 俄文 / 阿拉伯文 | 英文模型 ❌ |

日文汉字落在 CJK 区间里，纯字符统计区分不了。**用非中英文本检测，
结果不可信**——不是模型差，是它压根没为这些语言训练过。

### 换新主题的同类文体

实测：补了 92 条实用指南后，训练集内的识别率 30% → 78%，
但**我现场写的新指南仍然只有 2/5 能识别**。

这不是 bug，是 TF-IDF 的模型类别限制。要解决得换模型架构，不是加数据。

## 五、误报（把真人写成的东西判成 AI）

**这是它最在意的错误类型**。实测（HC3 数据集随机抽样）：

| 测试 | 误报率 | 中位 AI 概率 |
|---|---|---|
| 中文真人文本 500 条 | **0.4%**（2/500） | 0.040 |
| 中文真人文本 1000 条 | **0.5%**（5/1000） | 0.052 |
| 英文真人文本 497 条 | **9.1%**（45/497） | 0.085 |
| 英文真人文本 993 条 | **12.4%**（123/993） | 0.107 |

**中文约 0.5%，英文 9~12%。这个差距很大，必须说清楚。**

### 英文为什么会有 9~12%

我看了那 11 条误报，共同点是：**真人写的、但写得像教科书**。

举例（都是真人写的，被判 0.85~0.99）：

> "2 main reasons, both because of the Earth's rotation on its axis: 1. The earth moves faster at the equator... 2. To use the rotational velocity, the rocket must be launched eastward..."

> "In order to make sugars, a plant needs certain elements in its diet. It gets Carbon from the Carbon Dioxide in the air. It gets H2O from water. When it transfers in the water, it uses a tube in its stem, called the xylem..."

**结构清晰、术语密集、逻辑递进——这正是 AI 擅长的写法，也正是这类文本被误判的原因。**

对比：同样是科技内容，但写成口语就没问题：

> "So the way a microwave works is it just makes water molecules spin really fast, and that friction heats your food up. That's why a dry cracker barely warms but soup gets hot in a minute."

这段判 **0.264**（正确）。而 AI 写同一主题：

> "Microwave ovens operate by generating electromagnetic radiation at a frequency of approximately 2.45 GHz..."

这段判 **0.877**（正确）。

**结论**：模型判的是**措辞和结构**，不是"谁写的"。
真人按教科书风格写，就会撞枪口上。

### 所以正确的读法

- 中文：说「低」基本可信
- 英文：说「低」也不一定对，**真人写正式英文有 7% 概率被判高**
- 任何语言：说「高」不构成判决，只是"这段文字在措辞上很像 AI"

代价是**部分 AI 文本会漏判**。我们明确选择"宁可漏判，也不误伤"，
但英文这一侧误伤没有完全消灭，如实记录在这里。

## 六、降 AI 功能（改写器）

### 先说实话：它基本降不动

这是本页最重要的一节。

**规则改写对「论证型 AI 文本」几乎无效。** 实测（100 条 AI 论述文）：

| strength | 改写前 | 改写后 | 降幅 | 从「高」降到「中/低」 |
|---|---|---|---|---|
| 1.0 | 0.975 | 0.966 | 0.010 | **0/60** |
| 3.0 | 0.975 | 0.949 | 0.026 | **0/60** |
| 5.0 | 0.975 | 0.947 | 0.028 | **0/60** |

**把强度拉满也没用。**

### 为什么降不动

看这两个分布：

- 真人写的 300 条中文文本：AI 概率**中位 0.007**，95% 分位 0.155
- AI 写的 100 条论述文：AI 概率**中位 0.990**，最低 0.843

中间是**一条鸿沟**，不是渐变。

而这个检测器看的是 **TF-IDF 词频分布**——200 字的文本有两三百个词，
改写器改 3~8 处，词频分布几乎不动，分数也就不动。

**这不是实现不好，是方法本身的上限。**

### 那它到底能干什么

**公文/套话类**还有一点效果，因为这类文本里套话占比高，改掉几处就能动分布：

| 文体 | 改写前 | 改写后 | 从高降下来 |
|---|---|---|---|
| 公文通知 | 0.869 | 0.782 | 5/95 |
| 社交文体 | 0.625 | 0.516 | 3/29 |

**但「5/95」的意思是：95 条里只有 5 条降到了阈值以下。** 别抱太大期望。

### 一个重要的历史教训

早先版本在公文上能做到 0.804 → 0.244，看起来效果很好。

那是**靠把公文改成病句换来的**：

```
原文: 各部门：请高度重视，认真组织实施。
改写: 各部门：请看重，好好安排实施（我们试过）。
```

```
原文: 已经包括大量的数据集
改写: 已经里面有大量的数据集      ← 语法错误
```

**「降得动」的版本是坏的版本。** 现在它优先保证改完能读，代价是降不动。

### 真要降怎么办

用 **LLM 重写**——不是换词，是重新组织句子、改变论述顺序、加入个人化的表达。
那才能动到词频分布。

界面里的「LLM改写」选项就是这个，但它需要本地跑一个大模型（30B 级别的才够用），
在轻薄本上每条要几十秒。

而且**坦白说**：如果你的目的是绕过某个具体的检测系统，
那这件事本身就在跟那个系统的特征工程赛跑，没有终点。

## 七、怎么集成

### Python

```python
import sys; sys.path.insert(0, "src")
import model_zoo as M

M.warm_up()                          # 预热后每次 0.02ms
r = M.detect("要检测的文本……")
print(r["ai_probability"], r["bucket"], r["confidence"])
```

### HTTP

```bash
python src/serve.py        # http://127.0.0.1:8000

curl -X POST http://127.0.0.1:8000/detect \
  -H "Content-Type: application/json" \
  -d '{"text": "要检测的文本……"}'
```

### 指定档位

```python
M.detect(text, tier="tier0")     # 强制轻量档
```

默认 `auto`：按语言 + 机器性能自动选。

## 八、性能参考

| 项 | 数值 |
|---|---|
| 冷启动 | 约 0.43 秒 |
| 单次检测（热，tier1） | 0.035 毫秒 → **28000 次/秒** |
| 单次检测（热，tier0） | 0.20 毫秒 → 5000 次/秒 |
| 并发（8 线程混合） | 11177 次/秒，0 错误 |
| 内存占用 | 单档 0.4–2.8MB（权重文件） |
| 运行时依赖 | **只要 numpy** |

tier1/en 走 TF-IDF+LR，比 tier0 的 Hashing+NB 快一个数量级；
低配机自动落到 tier0，牺牲速度换内存。

---

## 九、一句话总结

**用它做参考信号，不要用它做判决。**

它能告诉你"这段文字在措辞上很像 AI"，这在很多场景下有用
（比如自查、批量筛查、给人工复核排优先级）。

但它判不了"这是不是 AI 写的"这种问题——
没有任何本地小模型能。任何声称能的人，要么在骗你，要么在骗自己。
